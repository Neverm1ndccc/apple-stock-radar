# Apple 来源适配与定时扫描（v0.4.0）

v0.2.3 界面更新：关注页及菜单栏小窗口可直接点击「启动扫描 / 关闭扫描」，设置页也使用同一控件。关闭停止后续调度，已发出的请求等待结束；启动调用已有显式恢复命令，继续遵守保护等待、请求间隔和预算。页面显示关闭、扫描中、下次扫描或停扫原因。

更新：2026-10-25。

## 当前状态

用户于 2026-10-25 明确同意修改项目规则，允许个人自动查询 Apple 商店非公开库存接口。v0.2.1 新增个人启用开关，不再要求以 Apple 许可文件冒充该选择。该同意仅为本项目使用选择，不代表 Apple 授权、公共 API 或可用性承诺。

接入包含 Apple 响应适配、地区/门店批次、可配置间隔、立即扫描、后台调度与错误停止。自动化检查继续全部离线；实际查询仅通过用户启用后的本机应用执行。首批结果记录在 TEST_REPORT.md。

## 间隔与调度语义

在「设置 → Apple 商店定时扫描」输入整数秒数后保存。默认 300 秒，配置范围 5–86400 秒；这是应用配置范围，不表示 Apple 允许这些频率。

同一地区、同一家店的最多 20 个 SKU 合为一个请求批次。优先选择包含最久未更新目标的批次，时间相同由游标公平轮转，重启仍参考持久化观测时间。每次请求完成后，等待 `max(设置间隔, 来源许可最低间隔, 已开启的低频保护下限)` 再执行下一批。目标较多时，一轮覆盖时间会增加；不能把每批请求间隔理解为每个目标都同频更新。

同一时刻最多一个库存请求，「立即扫描一批」也受请求预算约束。请求时间写入普通设置，进程重启或取消中的结果都不能绕过请求间隔；休眠后不补发积压请求。修改间隔后按上次请求完成时间重新计算。

v0.2.2 新增持久化令牌预算：容量 6 次，每 60 秒补充 1 次。请求发出前在 SQLite IMMEDIATE 事务中原子占用额度；成功、失败或取消都不退还。即时扫描、进程重启、普通设置更新与恢复旧备份不能补满额度。实际下次请求取间隔、额度恢复时间和失败等待时间的最晚值。用户保存的目标间隔保留，不会静默改写。

该预算参考 [Apple Pickup Watcher 的累计限流策略](https://github.com/ENCHIGO/apple-pickup-watcher/blob/d00eb0c8b691cb2345ff25c189bb4e5984ac7121/crates/apw-core/src/apple.rs)，采用更小的突发容量。上游经验和本应用参数都不是 Apple 公布的配额，也不能保证服务端不会拒绝访问。

应用暂停、切换来源、恢复备份、清理历史或修改关注后，旧请求结果不会再作为当前配置的有效结果落库。已发出的请求不能撤回，仍计入请求预算；拒绝和限流即使在配置变化期间返回，也会停止来源。

## 个人启用与接入边界

「设置 → Apple 商店定时扫描」中的“个人使用非公开库存接口”默认关闭。用户明确启用后，应用允许中港个人查询；再切换为 Apple 模式并开启后台扫描。个人启用状态只保存在本地普通设置，不创建虚构 Apple 许可记录。

已有真实来源许可时仍可读取独立目录中的 apple-authorization.json，受登记的机制、地区、最低间隔与期限约束。个人开关不会放宽已登记的来源配额或地区限制。

个人模式的 5 秒保护间隔只是应用最小值，不表示 Apple 允许该请求频率。推荐保留默认 300 秒，遇拒绝或限流立即停扫并持久保存原因，重启不会自动重试。仅明确的后台扫描开关可恢复；修改间隔或其他设置不能恢复被拒绝的来源。

请求使用普通 HTTPS 客户端、可识别的应用 User-Agent、连接/整体超时、禁重定向与 2 MB 响应上限。没有 Cookie 暖场、代理轮换、浏览器指纹伪装、验证码绕过或自动下单。

## v0.4.0 当前连接优化

- Apple 请求使用独立连接池、真实应用 UA 和普通 HTTPS/HTTP/2 ALPN 协商；可正常回落 HTTP/1.1。请求/通知客户端分离，没有 Cookie 暖场或浏览器伪装。
- 「低频连接保护」默认关闭；开启将有效间隔下限设为 180 秒。后台、立即扫描、重启和原子请求预约共同遵守，原用户间隔不改写；恢复备份保留当前更严格的保护。
- 响应若明确包含同地区、已启用关注门店及本次请求 SKU 的精确结果，则共享一次响应写入这些目标。缺失的额外门店或 SKU 不生成观测；门店重复、货号矛盾与未知字段不转换为有效库存。
- 设置展示协议、耗时和逐店完整覆盖估算。6 批 × 180 秒最坏约 18 分钟，超过默认 10 分钟有效期时提示风险；没有偷偷延长可信时间。响应复用可能缩短，但不保证实际返回多店。
- 可选停扫飞书故障通知独立于每目标有货开关，需全局飞书启用与 Keychain 可读；每次事故一次，不在重启后补发。详见 FEISHU.md。
- 参考同一锁定上游的实测经验：长期累积请求可能触发 541，改头或暖场也没有稳定保证。此处选择降低压力，所有真实拒绝仍立即停扫、人工恢复，不承诺永久修复非公开接口。

## 状态与失败

- 只把明确的 available / unavailable 映射为有货 / 无货。
- ineligible 标为 UNKNOWN / UNSUPPORTED，不把不支持取货当作无货。
- 缺门店、缺 SKU、货号矛盾、新字段值、错误信封或 HTML 页面均不能变为无货。
- 401 / 403 / 429 / 541、HTML 拒绝页面、协议异常、本地写入失败会停止来源；失败始终为 UNKNOWN。
- 拒绝/限流后保护等待依次为 5/10/20/30 分钟，失败计数和截止时间持久化。显式恢复不会重置失败计数，正常响应才清零。服务端 Retry-After 的秒数或 HTTP 日期不得被应用缩短。
- 网络/超时与标准 500/502/503/504 临时服务失败采用指数退避，应用退避上限 24 小时；服务端指定更久的等待仍优先。541 不归入临时服务失败。
- 停扫后不自动探测；人工处理并明确重新开启。来源恢复前的旧结果保持不可信，必须逐批重新获得有效观测。
- 自动查询使用独立 apple 来源，与 manual / mock 分开统计。前端不能伪造 Apple 观测；仅适配器写入。模拟不投递真实渠道。

## 数据升级

SQLite schema 升为 2，为 apple 来源扩展观测约束。打开 v1 库前先生成 `radar.pre-v2-<uuid>.sqlite` 备份，再事务迁移，保留目标、观测、事件和普通设置。v1 SQLite 备份也可验证并恢复到新版本。

恢复数据时关闭后台扫描、模拟和 Bark；保留当前库与备份中更严格的额度、拒绝原因和等待，避免旧备份绕过保护。升级后不应再用 v0.1 应用直接打开 v2 库；旧版需要对应的 v1 备份。

## v0.4.1 启停修复

普通网络/超时/临时服务错误的 scan_retry_after 只延后请求，不禁止用户开启调度。resume_after 仅在 scan_stop_reason 存在时表示人工恢复的保护期限。关闭后重开仍保留失败次数、预算和重试期限；后台/立即扫描/重启均不能提前请求。来源拒绝和限流等待不变。新增两项离线回归覆盖长退避启停与重启、原子预约及服务端限流期限。
